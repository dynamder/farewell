# 符号墨量匹配

> 一句话：每格不查亮度斜坡，而是问「这 64 个亚像素的剪影该配哪个字形」，颜色按形状重算。

## 0. 为什么换模型

`blit.packAscii` 取一格里的一个样本，`luma()` 查 `Options.ramp` 的十级索引。
一格只有十种状态、一种颜色，字符只负责「多黑」；候选集按亮度排序，与形状无关。
所以渐变出阶梯，边缘出锯齿。

**一个样本分不清「上暗下亮」和「均匀中灰」**，64 个可以。这就是这一档的全部前提。

## 1. 算法

每格 8×8 = 64 个采样，五步（`src/ink.zig`）：

| # | 做什么 | 函数 |
| --- | --- | --- |
| 1 | 取两色：通道跨度最大的那根通道上，最大像素与最小像素的**颜色端点** | `splitPair` |
| 2 | 做 64 位**剪影**：位 = 离 fg 比离 bg 近（平方欧氏） | `silhouette` |
| 3 | **短名单**：与每张字形掩码的 Hamming 距离，取前 `work` 个 | `choose` |
| 4 | **定案**：对每个候选按掩码重算两色（覆盖侧的均值当 fg，其余当 bg），算重建误差 | `score` |
| 5 | 取误差最小的候选 | `choose` |

第 4 步是重点：**字形决定形状，两个均值决定颜色**。一个 50% 灰的格子会拿到约 50%
覆盖的字形，配上两个只差一点的灰，看起来就是抗锯齿。

`score` 的误差不是第二次遍历样本算的，而是从已经累积的两侧色和、能量代数展开：
`Σ|p−c|² = Σ|p|² − 2(fg·S₁ + bg·S₀) + n₁|fg|² + n₀|bg|²`。对任意两色成立，所以结果和
逐样本求和逐位相同——有一条测试拿整张表对拍。

## 2. 表：一半算，一半量

| 来源 | 内容 | 数量 | 依赖字体？ |
| --- | --- | --- | --- |
| `src/ink.zig` 里 comptime 算 | U+2580..U+259F 块字符 | 29 | 否 |
| `src/ink-ascii-8x8.zig` 量出来 | ASCII 0x20..0x7E | 93 | 是 |

**块字符必须算。** 它们的定义就是「格子下 k/8 涂满」，8×8 网格正好一格对一档。
实测（`tools/inkmap.py` 从 CascadiaMono 渲染）会把 U+2584 和 U+2585 放到同一张掩码上——
字体把块画得比 cell 小一点，量化就塌，色调阶梯直接白掉一档。用 `rows()`/`cols()` 算就没有
这个问题，而且这条恒等可以在测试里断言（U+2588 必须全 1）。

**ASCII 只能量。** `g`、`%`、`@` 的形状没有解析定义。

同一张渐变（120×36）跑三个档位，取整幅平均色：

| 档位 | 平均 RGB | render/帧 |
| --- | --- | --- |
| 源 | 128, 128, 100 | — |
| `ascii` | 14, 15, 10 | 0.06 ms |
| `half` | 124, 126, 97 | 0.07 ms |
| `ink` | 124, 126, 97 | 4.48 ms |

`ascii` 档不只是出阶梯，它是**暗一个量级**：`bg` 恒为黑，字形只盖住一格的一部分，于是
「亮度」上不去。这一档的亮度本来就该由覆盖率×两色决定，而不是由「多黑的字符」决定——
这正是 `ink` 的模型。`half` 和 `ink` 都落在源上，因为它们的两个颜色都取自源。

表是 `blocks ++ measured`，每张 121（8×8）或 123（8×16）个字形。

### 已知的两处边界

- 字母的墨迹在 10×20 的 cell 里只占中间约 3/8 行（x-height 的真实位置），所以字母形状在
  8×8 下判别力有限。色调靠块字符，字母只补边缘和纹理。
- 量出来的表里 `-`≡`~`、`=`≡`m` 完全同掩码。匹配器分不出来，所以生成器把后出现的那个
  丢掉，并在文件头记下被丢的码点。

## 3. 网格是一族选项

网格是匹配器的编译期参数（`ink.Grid`），每个网格是一个档位：

| 档位 | 网格 | 采样/格 | ASCII 字形 | 掩码宽度 | 匹配器 |
| --- | --- | --- | --- | --- | --- |
| `ink` | 8×8 | 64 | 93 | u64 | ~1.0 µs/格 |
| `ink16` | 8×16 | 128 | 95 | u128 | ~2.0 µs/格 |

8×16 在 10×20 的 cell 里子格是正方形，字母的墨迹从三行变成六行，而且表里**没有任何掩码
碰撞**（8×8 下 `m` 和 `~` 会撞）。看起来该更好，实测不然。

拿 600 个合成格子（随机方向的边缘、渐变、圆盘、噪声），两者都按 8×16 还原到同一个源上：

| 图案 | 8×8 误差 | 8×16 误差 | 比值 |
| --- | --- | --- | --- |
| 边缘 | 800,308 | 799,285 | 1.001 |
| 渐变 | 484,803 | 484,761 | 1.000 |
| 圆盘 | 830,134 | 843,149 | 0.985 |
| 噪声 | 144,052 | 153,051 | 0.941 |

比值 > 1 表示 8×16 更好。结论：**没有提升，噪声上甚至更差**——8×8 的两行平均本身在降噪。

原因是这一层的残差大头不是边界位置，而是**一侧内部的颜色散布**：一格只有两种颜色，边界
挪半行不会改变两侧各自的方差。换句话说，瓶颈是「两种颜色」，不是「网格多细」。这条实测
把「更细的网格 ⇒ 更准」这个直觉否掉了，也说明下一级质量要么来自更多颜色（终端给不了），
要么来自更好的边界形状（更多方向、更长的表）。

## 4. 生成与检查

```
zig build                # 不碰 Python
zig build inkmap         # 重新生成 src/ink-ascii.zig（需要 Pillow + 一个字体）
zig build inkmap-check   # 校验表没和工具脱节（不需要字体，不需要 Pillow）
```

生成器是 Python：掩码要从字体渲染，而 Zig 标准库没有字体光栅器，这是唯一的理由。
生成物入库，`zig build` 永远不跑这一步。

`--check` 比对的是生成文件里记录的**脚本哈希**和**参数**。这两样正是「改了工具或参数却忘了
重生成」时唯一会变的东西，而且不需要字体就能查——CI 因此在 ubuntu 上跑一行 `python3` 即可。
带 `--font` 时它才会重渲染、逐值比对。

## 5. 代价（120×36 = 4,320 格，ReleaseFast，120 帧）

| 场景 | 档位 | render/帧 | 字节/帧 |
| --- | --- | --- | --- |
| gradient | ascii | 0.07 ms | 673 |
| gradient | half | 0.07 ms | 1,311 |
| gradient | **ink** | 4.55 ms | 1,311 |
| gradient | **ink16** | 8.28 ms | 1,311 |
| raymarch | half | 1.56 ms | 19,617 |
| raymarch | **ink** | 39.6 ms | 20,640 |
| raymarch | **ink16** | 46.3 ms | 21,292 |

两件事要分开看：

- **匹配器本身约 1.0 µs/格（8×8）、2.0 µs/格（8×16）**。gradient 那几行隔离出来的就是它
  （廉价源，采样几乎不要钱）。这是 `表长次 popcount + work × 采样数 次累积` 的价格，
  `work = 1` 能把后一半砍掉。
- **raymarch 那行的 40 ms 里，约 35 ms 是场景被求值 64 次**，不是匹配器的账。源越贵，这一档
  越贵；`Frame` 源每样本只是内存读，代价会低一个数量级。

顺带一个有用的证据：平滑的垂直渐变上，ink 输出的字节数和 half **完全一样**（1,311）。
因为它选出来的就是上下半块、颜色就是两半的均值——这一档不会在平滑区域凭空长纹理。
平坦格子同理：选空格、fg = bg，不许长网点（有测试守着）。

## 6. 来源与许可

算法思路参考 chafa（LGPL）的 `chafa-work-cell.c` 与 `chafa-symbol-map.c`，只取方法：

- 那个仓库的匹配核心约 100 行（`insert_candidate` + `find_candidates`），其余 1800 行是
  selector 语法和 tag 集合，本仓库不需要也没有对应实现。
- **没有复制它的字形表**（`chafa-symbols-ascii.h`，1361 行手画轮廓，LGPL 且绑 Terminus）。
  我们的表由 `tools/inkmap.py` 从系统字体渲染得出，粒度都不同（它是轮廓，我们是覆盖率）。
- 实现是独立写的：函数分解、候选选择、误差计算、反色候选（未做）都不同。

字形掩码是字体渲染输出，OFL 不管渲染结果；仓库只分发每字 8 或 16 字节的指纹，不分发字体文件。
`glyphs` 参数存在，就是给「字体不同」留的出口——宿主可以拿同一份工具生成自己的表。

## 7. 未决

- **两种颜色是上限**：§3 的实测说明网格不再是瓶颈。要提高保真度，要么让一格能表达三种
  颜色（终端给不了），要么让边界形状更丰富（更多方向、更长的表），要么把误差交给跨格手段
  （抖动）。这条是下一步所有质量讨论的出发点。
- **`work` 默认 4**：`work = 1` 快一半，代价是偶尔选到次优字形（短名单是启发式，只保证
  「候选内最优」）。
- **阴影块 U+2591..U+2593**：25/50/75% 的棋盘格，是现成的中间调字符；但字体可能把它们画成
  实心灰而不是点阵，需要先验一下再决定收不收。
